Beyond Cloud Brand Intelligence Automation
30-Day Project Proposal & Delivery Expectations
Project Name: Beyond Cloud Brand Intelligence Automation Platform
Duration: 30 Days
Prepared For: Beyond Cloud Internal Product Development Team
Objective: Build an automated brand intelligence platform that continuously monitors digital channels for brand abuse, phishing, impersonation, rogue applications, sensitive document exposure, and unauthorized brand/logo usage.

________________________________________

## 1. Project Objective

The goal is to develop a centralized automation platform that can:

- Continuously discover and monitor suspicious domains related to client brands.
- Detect phishing infrastructure and active phishing campaigns.
- Identify fake or unauthorized mobile applications.
- Monitor social media platforms for impersonation accounts and fraudulent activity.
- Detect exposure of sensitive documents related to monitored brands.
- Identify unauthorized use of brand logos across websites.
- Generate alerts, dashboards, and evidence for analyst review.

The first release should be production-ready for internal analyst usage within 30 days.

## 3. Module-wise Expectations

### 3.1 Phishing Domain Monitoring

**Purpose:** Detect domains attempting to impersonate client brands.

**Typosquat Monitoring**

- Generate typo variants using common patterns:
  - character omission
  - character substitution
  - transposition
  - homoglyphs
  - added prefixes/suffixes
- Monitor newly registered domains against generated variants.
- Support .com, .in, .net, .org, .co, and country TLDs.

**MX Record Monitoring**

- Resolve MX records for suspicious domains.
- Flag domains configured for email delivery.
- Risk scoring:
  - No MX = Low
  - MX configured = Medium
  - MX + active website = High

**Active Phishing Domain Detection**

- Check for active HTTP/HTTPS response.
- Capture page title, favicon hash, screenshot, and SSL certificate details.
- Compare favicon hash with legitimate brand favicon.
- Detect keywords such as login, secure, account, verify, payment, etc.
- Mark domains as Suspected Phishing when similarity score exceeds threshold.

**Expected Output**

| Field | Description |
|---|---|
| Domain | Suspicious domain |
| Similarity Score | 0–100 |
| MX Enabled | Yes/No |
| Website Live | Yes/No |
| SSL Present | Yes/No |
| Screenshot | Captured image |
| Risk Level | Low / Medium / High / Critical |

### 3.2 Fake APK Monitoring

**Purpose:** Identify Android APK files pretending to be official client applications.

**Features**

- Search public APK repositories and indexed APK sources.
- Match package names against official package list.
- Detect:
  - similar app names
  - similar package identifiers
  - reused icons/logos
  - suspicious developer names
- Extract metadata:
  - app name
  - package name
  - version
  - developer/publisher
  - download source
  - SHA256 hash (if available)

**Expected Output**

| Field | Description |
|---|---|
| App Name | Discovered app |
| Package Name | Android package |
| Similarity Score | Brand similarity |
| Source | Repository URL |
| Logo Match | Yes/No |
| Risk Level | Medium / High |

### 3.3 Rogue Mobile Application Monitoring

**Purpose:** Detect unauthorized mobile apps listed on official app stores.

**Features**

- Monitor Google Play Store search results for brand keywords.
- Compare app publisher with approved publisher list.
- Flag applications using brand name, logo, or product terminology without authorization.
- Track app status changes (new, removed, updated).

**Expected Output**

| Field | Description |
|---|---|
| Store | Google Play |
| App Name | Discovered app |
| Publisher | App publisher |
| Official Publisher Match | Yes/No |
| Install Count | If available |
| Risk Level | Medium / High |

### 3.4 Social Media Impersonation Monitoring

**Purpose:** Detect fake or impersonating social media accounts.

**Platforms (Phase-1):** X (Twitter), Facebook, Instagram, LinkedIn, Telegram (public channels/usernames)

**Detection Logic**

- Username similarity
- Display name similarity
- Profile image/logo similarity
- Bio/description containing brand name
- Use of official support/contact terminology

**Expected Output**

| Field | Description |
|---|---|
| Platform | Social platform |
| Username | Account handle |
| Display Name | Profile name |
| Similarity Score | 0–100 |
| Logo Match | Yes/No |
| Followers | If available |
| Risk Level | Low / Medium / High |

### 3.5 Sensitive Document Monitoring

**Purpose:** Identify publicly exposed documents containing client brand references.

**Sources**

- Search engine indexed documents
- Public file-sharing links
- Exposed PDF/DOC/XLS/PPT files accessible without authentication

**Detection Logic**

- Brand keyword match
- Domain match
- Email address pattern match
- Filename pattern analysis (confidential, internal, salary, customer, etc.)

**Expected Output**

| Field | Description |
|---|---|
| Document Name | File name |
| File Type | PDF/DOC/XLS/PPT |
| URL | Public location |
| Brand Match | Matched keyword |
| Exposure Confidence | Low / Medium / High |
| Risk Level | Medium / High / Critical |

### 3.6 Brand Logo Mentions on Websites

**Purpose:** Detect websites using the client's logo without authorization.

**Features**

- Crawl discovered suspicious domains and websites.
- Extract images from pages.
- Compute perceptual hash (pHash) for logo comparison.
- Match against stored official brand logos.
- Capture screenshot evidence when a match is found.

**Expected Output**

| Field | Description |
|---|---|
| Website | Detected website |
| Page URL | Specific page |
| Logo Match Score | 0–100 |
| Screenshot | Evidence image |
| Risk Level | Medium / High |

# Addendum (owner, 2026-10-09) — Important additional requirements (verbatim)

> Received 2026-10-09. Mandatory; applies to the entire implementation together with everything above.
> Traced in `01-requirements-register.md` section Q (IDs RDA-01…RDA-23).

## 1. NO DEMO DATA / NO MOCK SECURITY FINDINGS

This must be a REAL working security/brand-intelligence platform.

DO NOT create or use demo/mock/fake data for the actual application.

Do NOT add: Fake domains; Fake phishing websites; Fake APKs; Fake social accounts; Fake documents; Fake threat-intelligence results; Fake screenshots; Fake risk scores; Fake alerts; Fake scan results; Hard-coded security findings; Fake dashboard statistics; Fake API responses; Fake fallback findings.

The dashboard must display ONLY: Real scan results; Real database records; Real findings generated by implemented scanners; Real threat-intelligence responses; Real evidence collected by the system.

If there are no findings, display: "No threats detected."

Do NOT create fake findings just to make the dashboard appear populated.

### External service unavailable

If an external service/API/tool is: Not configured; Rate limited; Unavailable; Failed; Not installed; Authentication missing — DO NOT generate fake results.

Instead: Show the integration status. Record the error. Continue with other available scanners where possible. Clearly indicate which detection sources were unavailable. Store scan/tool execution status.

```text
Domain Discovery       ✓ Completed
DNS Analysis           ✓ Completed
HTTP Analysis          ✓ Completed
Playwright Analysis    ✓ Completed
PhishTank              ⚠ Not Configured
urlscan.io             ⚠ API Unavailable
```

Never convert an unavailable integration into a fake "no threats found" result.

## 2. TEST DATA MUST NEVER ENTER THE REAL APPLICATION

Automated tests may use fixtures/factories/test data when necessary. However: Test data must remain inside test code. Test fixtures must not automatically seed the development database. Test fixtures must not appear in the real dashboard. Production APIs must never return test findings. Do not create a `mockData.ts` or equivalent and use it as a production fallback. Do not automatically populate MongoDB with fake security findings.

The application must work correctly with an empty database. An empty database is a valid state.

## 3. FIRST INSPECT EXISTING IMPLEMENTATION

Before writing new code, inspect the entire existing repository. Identify: Existing frontend modules; Existing backend modules; Existing scanners; Existing APIs; Existing database models; Existing MongoDB collections; Existing workers; Existing schedulers; Existing risk/scoring logic; Existing alert logic; Existing evidence storage; Existing dashboard components; Existing investigation pages; Existing integrations; Existing authentication/authorization; Existing tests.

Create an internal understanding of what already exists before modifying the code. DO NOT blindly create new modules for functionality that already exists.

## 4. EXISTING FEATURES MUST BE ENHANCED, NOT DUPLICATED

If a requested feature already exists in the project: DO NOT create a second implementation. Instead: 1. Inspect the existing implementation. 2. Understand how it currently works. 3. Identify its limitations. 4. Improve it. 5. Extend its detection capabilities. 6. Improve its accuracy. 7. Improve its evidence collection. 8. Improve its scoring. 9. Improve its alerting. 10. Add missing integrations. 11. Add missing error handling. 12. Add tests.

For example: If domain scanning already exists: DO NOT create another unrelated domain scanner. Instead improve the existing scanner with: Better typosquat detection; Better homoglyph detection; DNS analysis; HTTP/HTTPS analysis; Redirect analysis; Website content analysis; Login detection; Brand keyword detection; Logo detection; Threat-intelligence correlation; Evidence collection; Historical comparison; Deduplication; Risk calculation; Confidence calculation.

The same principle applies to every existing feature.

## 5. IMPROVE EXISTING SCANNERS

For every existing scanner, perform a quality review. Check: What does it currently detect? What signals does it collect? What signals are missing? Are results real? Is the scanner reliable? Are results normalized? Are duplicate findings created? Is evidence stored? Is historical information stored? Is scoring accurate? Is confidence calculated? Are false positives handled? Are failures handled correctly? Are external integrations used correctly? Is the scanner correlated with other modules? Does the scanner generate actionable alerts?

Then improve the implementation. Do not assume that an existing scanner is already complete simply because the feature exists.

## 6. ACCURACY IS MORE IMPORTANT THAN NUMBER OF ALERTS

The goal is NOT: "Generate as many alerts as possible." The goal is: "Generate accurate, evidence-backed, explainable alerts with minimum reasonable false positives."

A suspicious indicator alone should not automatically become a critical alert. For example: `Domain similarity = 95%` does NOT automatically mean: `CRITICAL PHISHING`. The system must investigate additional signals.

## 7. MULTI-SIGNAL DETECTION

Improve scanning so risk is calculated from multiple independent signals. For website/domain threats, consider signals such as:

- **Domain signals:** Exact brand keyword; Typosquat similarity; Homoglyph; Character insertion; Character deletion; Character replacement; Character transposition; Suspicious TLD; Brand + login; Brand + payment; Brand + security; Brand + verify; Brand + account.
- **DNS/infrastructure signals:** A record; AAAA record; MX record; NS record; CNAME; IP address; ASN; Hosting information; DNS age/history where available; Infrastructure reuse; Suspicious nameservers.
- **Website signals:** Website active; HTTPS; Redirect chain; Final destination; Brand name; Brand logo; Login form; Username field; Password field; OTP field; Payment field; Credential collection; Suspicious JavaScript; External resources; Suspicious URLs; Page title; Website technologies.
- **Threat-intelligence signals:** PhishTank; OpenPhish; urlscan.io; Google Safe Browsing / Web Risk where applicable; Other configured threat feeds.
- **Visual signals:** Logo similarity; Favicon similarity; Screenshot similarity where implemented.

The scoring system must combine these signals rather than relying on one simple rule.

## 8. IMPROVE RISK SCORING

Review and improve all existing scoring logic. Do NOT use simplistic rules such as: `similarity > 80% = phishing`, or `MX record exists = malicious`, or `HTTPS exists = malicious`. These are signals, not proof.

Maintain separate concepts: 1. **Risk Score** — How dangerous the finding appears to be. 2. **Confidence Score** — How confident the system is that the classification is correct. These must NOT be treated as the same value.

For example: A domain can have `Risk: 75 / Confidence: 35` when it looks suspicious but evidence is weak. Another finding can have `Risk: 92 / Confidence: 96` when multiple independent sources confirm malicious behavior.

## 9. EXPLAINABLE SCORING

Every score must have an explanation. Instead of `Risk Score: 94`, store/display:

```text
Risk Score: 94/100

Reasons:
+10 Domain similarity: 94%
+05 Brand keyword detected
+08 Login form detected
+05 Password field detected
+15 Official logo similarity: 93%
+10 Suspicious redirect chain
+20 Threat-intelligence match
+08 Active HTTPS phishing page
+13 Correlated indicators
```

The exact weights may be adjusted based on the existing scoring system, but every score must be traceable to actual evidence. Do not create arbitrary unexplained scores.

## 10. FALSE POSITIVE REDUCTION

Improve the system to reduce false positives. Consider: Multiple independent signals; Evidence quality; Source reliability; Confidence; Domain activity; Historical observations; Known legitimate domains; Brand-owned domains; Trusted partners; Analyst decisions; Threat-intelligence confidence; Duplicate findings; Cross-module correlation.

Support analyst decisions such as: Confirmed Threat; False Positive; Legitimate; Ignored; Investigating; Reopened.

Analyst decisions should be preserved and used as historical context where appropriate.

## 11. EXACT ALERT GENERATION

An alert should only be generated when the finding meets the configured alert criteria. Do NOT generate an alert simply because a candidate was discovered. Separate: Candidate → Finding → Alert.

- **Candidate:** "Possible typosquat detected. Similarity: 91%" — This may require further scanning.
- **Finding:** After additional analysis: "Domain active; Brand name detected; Login form detected; Logo similarity 91%" — Now the system has stronger evidence.
- **Alert:** If risk/confidence thresholds are met: "HIGH — Possible Brand Phishing; Risk: 84/100; Confidence: 91/100".

This distinction must be implemented wherever applicable.

## 12. ALERT MUST SHOW WHY IT WAS CREATED

Every alert must contain actionable information. Minimum alert information: Alert ID; Finding ID; Brand; Threat type; Target; Risk score; Confidence score; Severity; Detection time; First seen; Last seen; Detection reasons; Evidence; Scanner/source; Related indicators; Threat-intelligence matches; Screenshot where applicable; DNS evidence where applicable; HTTP evidence where applicable; Redirect chain where applicable; Logo similarity where applicable; Domain similarity where applicable; Related findings; Scan ID; Current analyst status.

Example: "CRITICAL — Active Brand Phishing; Target: https://example-brand-login.com; Risk: 94/100; Confidence: 96/100; Reasons: 94% domain similarity, Official brand name detected, Official logo similarity: 93%, Login form detected, Password field detected, Active HTTPS, Suspicious redirect chain, Threat-intelligence match; Evidence: Screenshot, DNS records, HTTP response, Redirect chain, Logo comparison, Threat-intelligence result."

The user must be able to understand the alert without opening the source code.

## 13. DO NOT DOUBLE-COUNT THE SAME EVIDENCE

Multiple scanners may discover the same threat. For example: Subfinder, Amass, crt.sh, Search engine may all discover `suspicious.example.com`. This should NOT create four independent findings. Normalize and correlate the results. Multiple sources may increase confidence, but do not blindly multiply the risk score.

Similarly correlate: Same domain; Same URL; Same APK SHA256; Same IP; Same certificate; Same social account; Same document hash; Same logo; Same infrastructure — where appropriate.

## 14. RESCAN EXISTING FINDINGS INTELLIGENTLY

When a scheduled scan discovers an entity that already exists: DO NOT blindly create another finding. Instead: 1. Match against the existing entity. 2. Store a new observation. 3. Update `last_seen`. 4. Compare previous and current state. 5. Detect changes. 6. Recalculate risk. 7. Recalculate confidence. 8. Update the finding. 9. Generate a new alert only when a meaningful change or threshold crossing occurs.

Examples of important changes: Previously inactive domain → active website; Previously no login form → login form detected; Previously no logo → official logo detected; Previously no threat intelligence → threat intelligence match; Previously Low risk → High risk; Previously unknown APK → certificate mismatch discovered.

These changes should appear in the finding timeline.

## 15. CROSS-MODULE CORRELATION

Improve the existing correlation engine. Example: Suspicious Domain → Phishing Website → Fake APK contains same domain → Social account uses same logo → Exposed document contains same URL. These should be correlated into a potential campaign:

```text
Threat Campaign #123

├── Suspicious Domain
├── Phishing Website
├── Fake APK
├── Social Impersonation
└── Exposed Document
```

Cross-module correlation should increase confidence when independent evidence supports the same threat.

## 16. SCAN STATUS MUST BE REAL

Never show a scan as successful when it actually failed. Use states such as: queued; running; completed; completed_with_errors; partially_completed; failed; cancelled.

For every scan show which components succeeded or failed:

```text
Domain Discovery       ✓ Completed
DNS Analysis           ✓ Completed
HTTP Analysis          ✓ Completed
Browser Analysis       ✓ Completed
Threat Intelligence    ⚠ Not Configured
Logo Analysis          ✓ Completed
```

Do not hide failures. Do not convert tool failures into fake successful results.

## 17. REAL EVIDENCE STORAGE

Whenever possible, preserve evidence supporting the finding. Examples: Screenshots; HTML; DNS records; HTTP headers; Redirect chain; URLs; Domain information; IP/ASN; Threat-intelligence response; APK SHA256; APK metadata; Certificate fingerprint; Permissions; Extracted URLs; Social profile information; Document metadata; Logo comparison; Scan logs. Evidence must be associated with the correct finding.

## 18. EXISTING DASHBOARD MUST USE REAL BACKEND DATA

Review all dashboard pages and remove any hard-coded statistics or fake records. Data that must come from the backend: Total findings; Critical alerts; High-risk findings; Domain count; Phishing count; APK count; Social impersonation count; Document findings; Active campaigns; Recent alerts; Risk trends; Scan history.

If there are zero findings: `Critical Alerts: 0 / High Risk: 0 / Active Threats: 0`. Do not display artificial numbers.

## 19. NO FAKE FALLBACK LOGIC

Avoid code such as `data || mockData`, or `if (!apiResponse) { return demoFindings; }`, or `const findings = response?.findings || sampleFindings;`. If the backend returns no data, display an empty state. If the backend fails, display an appropriate error state.

## 20. SCANNER QUALITY STANDARD

Every scanner/module should follow this lifecycle: Discovery → Validation → Normalization → Deduplication → Analysis → Evidence Collection → Risk Calculation → Confidence Calculation → Correlation → Persistence → Alert Decision → Analyst Workflow.

Do not implement scanners that only return `{"suspicious": true}`. Return structured evidence and explain why the finding was classified.

## 21. SECURITY TOOL FAILURE HANDLING

External tools such as: Subfinder; Amass; dnsx; httpx; Nuclei; MobSF; YARA; Playwright; APK analysis tools; Threat-intelligence APIs — must be treated as integrations.

If a tool fails: Capture the error. Record execution status. Continue with other independent scanners where safe. Do not fabricate the missing output. Do not mark the tool as successful. Do not create findings from nonexistent results.

## 22. FINAL IMPLEMENTATION PRIORITY

When implementing or modifying features, prioritize in this order: 1. Existing functionality preservation 2. Real data collection 3. Detection accuracy 4. Evidence collection 5. Risk scoring 6. Confidence scoring 7. Correlation 8. False-positive reduction 9. Accurate alerts 10. Analyst workflow 11. Dashboard presentation 12. Performance/UX improvements.

Do NOT prioritize visual dashboard completeness over actual detection accuracy.

## 23. FINAL RULE

The platform must behave like a real security product. The system should prefer `No threat detected` over `Fake threat detected`, and `Unable to scan — tool unavailable` over `Scan successful`, and `Suspicious candidate — insufficient evidence` over `Critical phishing alert` when the evidence does not justify the stronger classification.

The ultimate goal is: REAL SCANNING + REAL DATA + REAL EVIDENCE + IMPROVED EXISTING FEATURES + ACCURATE SCORING + CONFIDENCE + CORRELATION + LOW FALSE POSITIVES + EXACT, ACTIONABLE ALERTS.
